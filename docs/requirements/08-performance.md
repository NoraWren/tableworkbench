# 08 性能

这一章是硬约束。任何功能实现如果过不了这里的数字，要么优化，要么砍掉，不允许"先跑通再说"。

## R-PERF-01 打开速度

- 优先级：P0
- 状态：已完成
- 行为：从松手到表格可滚动的时间上限。
- 验收：
  - [x] 500 MB CSV 首次打开不超过 2 秒（不含后台转 Parquet 完成；8 次冷打开中位 1.546 秒，范围 1.527–1.851，bench.sh 复跑 1.834 秒，见 R-DEC-15）
  - [x] 同一个文件第二次打开不超过 1 秒（实测 0.79–0.84 秒）
  - [x] 1 GB Parquet 打开不超过 2 秒（实测 1.76 秒）
  - [x] 1000 万行、20 列 Parquet 打开不超过 3 秒（改成视图后 0.028 秒，见 R-DEC-17）
- 测量方法：脚本记录进程启动到首屏绘制的墙钟时间，输出为表格，纳入 bench.sh。
- 边界：冷启动不含在应用内打开文件，冷启动单独算，见 R-PERF-04。
- 依赖：R-IMP-05、R-PERF-05

## R-PERF-02 缓存转换耗时

- 优先级：P1
- 状态：已完成
- 行为：后台把 CSV 转 Parquet 的耗时，用户能继续用，但转换不能无限拖。
- 验收：
  - [x] 500 MB CSV 转 Parquet 不超过 20 秒（release，三次 3.685–3.888 秒，见 bench-history）
  - [x] 转换期间滚动和筛选仍然可用（同时转换下滚动 p95 1.13 ms，超预算帧 0；筛选返回 652,606 行）
  - [x] 转换中退出应用不损坏源文件（kill -9 后源文件 md5 不变，正式缓存不存在；遗留 .tmp 由启动清扫）
- 测量方法：scripts/bench-cache.sh，口径是后台任务启动到产物改名完成，不含进程启动与编码探测。
- 边界：不做多线程分片转换，先单线程，够用就停。
- 依赖：R-IMP-05

## R-PERF-03 滚动与交互

- 优先级：P0
- 状态：已完成
- 行为：滚动和点击必须跟手。
- 验收：
  - [x] 1000 万行垂直滚动稳定在 60 fps，掉帧率低于 5%（20 列：p95 2.97 毫秒，超 16.7 毫秒的帧 0.2%）
  - [x] 100 列 × 1000 万行横向滚动不掉帧（100 列自绘后 p95 3.09 毫秒，超预算 0.3%）
  - [x] 点击一行到选中态出现不超过 50 毫秒（release，三份数据各 40 次：p95 3.08 / 2.92 / 2.82 毫秒，最大 45.1 毫秒，超预算 0 次，见 bench-history）
- 测量方法：Instruments 的 Core Animation 和 Time Profiler；没有 Xcode 时滚动用 scripts/bench-scroll.sh，口径是主线程每帧的布局与绘制耗时；点击用 scripts/bench-click.sh，口径是「按下 → 该行进选中集 → 受影响行重绘完」，不含显卡合成与垂直同步。
- 边界：不做逐帧打点上报。
- 依赖：R-GRID-01、R-GRID-02

## R-PERF-04 包体积与启动

- 优先级：P0
- 状态：已完成
- 行为：这两个数字直接写进 README 第一屏，必须诚实。
- 验收：
  - [x] dmg 不超过 30 MB（release 构建实测 15 MB）
  - [x] 解压后 app bundle 不超过 60 MB（release 构建实测 53 MB）
  - [x] 冷启动到窗口可交互不超过 0.6 秒（2026-10-27 release 跑八批共 152 轮，去掉每批首轮后中位 0.497 秒、最小 0.465、最大 0.563、p95 0.537，超预算 0/152。前后十来批里另有 2 次擦线超，分别在负载 24.5 和 Codex 自己占 70% CPU 时，见 bench-history）
- 说明：如果 DuckDB 静态链接后包体积超过 30 MB，先把目标调成 40 MB 并写进 README，不许隐藏。
- 测量方法：`./scripts/bench-launch.py --rounds 20`，从 `open -a` 返回到 CGWindowList 里出现带标题的主窗口，忙等。口径与分段归因见 `docs/bench-history.md` 的「冷启动（2026-10-27）」。
- 边界：不为省体积裁剪 DuckDB 功能。
- 依赖：R-REL-01

## R-PERF-05 基准数据集

- 优先级：P0
- 状态：已完成
- 行为：scripts/make-bench-data.sh 生成固定数据集，所有人跑同样的数据。
- 数据集四份：
  - 500 MB CSV，约 800 万行，20 列，含中文、空值、日期。
  - 1 GB Parquet，由上一份转换而来。
  - 1000 万行 × 20 列 Parquet，用于滚动测试。
  - 20 MB xlsx，3 个工作表，含合并单元格和公式。
- 验收：
  - [x] 脚本在空目录能一键生成全部四份（2026-10-27 清空 bench-data 后重跑，约 3 分钟出全部十份：四份规定数据、三份 CSV 中间产物、三份辅助样本）
  - [x] 生成的数据行数、列数、文件大小写进 bench.sh 的输出（见下方实测表）
  - [x] 数据集不进 Git 仓库，加进 .gitignore
- 边界：不用真实用户数据做基准。
- 依赖：R-PERF-01

实测（2026-10-27，release 版 TableWorkbenchBench，路径是 bench-data/）：

| 数据集 | 大小 | 行数 | 列数 | 说明 |
|---|---|---|---|---|
| 500mb.csv | 500.1 MB | 3,266,000 | 20 | 中文、空值、日期齐全 |
| 500mb.parquet | 130.4 MB | 3,266,000 | 20 | 由上一行转换，导出 1.216 秒，回读 0.028 秒 |
| 1gb.csv | 1024.1 MB | 6,688,000 | 20 | |
| 1gb.parquet | 267.1 MB | 6,688,000 | 20 | 导出 3.142 秒，回读 0.023 秒 |
| 10m.csv | 1550.3 MB | 10,124,000 | 20 | |
| 10m.parquet | 404.3 MB | 10,124,000 | 20 | 导出 6.016 秒，回读 0.021 秒 |
| sample-20mb.xlsx | 21.3 MB | 99,023 | 多表 | 数据 74,000 行 / 汇总一 20,022 行 / 汇总二 5,001 行；含合并单元格与无缓存值的公式 |
| wide-100k.csv | 15.0 MB | 100,000 | 20 | 小样本，端到端用例用它 |
| gbk-sample.csv | 0.6 MB | 5,000 | 20 | GB18030 编码，验编码探测 |
| wide-3000.csv | 5.2 MB | 200 | 3000 | 宽表，验 200 列显示上限与宽表滚动 |

CSV 实际行数比需求写的「约 800 万行」少一半，原因是这一版数据集每条记录字段更多、平均行长约 160 字节，
500 MB 装不下 800 万行。行数列数都照实写进 bench.sh，没有为了对上门槛去删列。

Parquet 不依赖外部 duckdb 命令行，由应用自己的导出通道（TableWorkbenchBench --export-parquet）生成，
免得基准数据和被测代码用两套 Parquet 写法。

## R-PERF-06 内存

- 优先级：P1
- 状态：已完成
- 行为：打开大文件后的常驻内存要可预期。
- 验收：
  - [x] 打开 1 GB 文件后常驻内存不超过 1.5 GB（峰值 RSS 1.30 GB，常驻只会更低）
  - [x] 转码不整文件读入：155 MB 的 GB18030 文件峰值 RSS 224 MB（旧实现 601 MB）
  - [x] 连续打开关闭 20 个大文件，内存回到基线附近（允许 ±200 MB）
        实测三次：静置 60 秒后相对空载基线 +63 / −30 / −144 MB，全部在范围内，见 bench-history
  - [x] 不做任何操作放 30 分钟，内存不上涨
        10m.parquet 保持打开静置 1800 秒：起始 62 MB，末值 1 MB，全程最大涨幅 +0 MB，判定通过
- 测量方法：scripts/bench-memory.sh（加 --long 跑 30 分钟那条）。判定只看匿名页（task_vm_info.internal），
  RSS 与文件页只打印不参与判定；基线取「每个文件都热过一遍之后」的空载值；判定读静置后的稳态值。
  为什么这样定口径见 bench-history「内存（2026-10-27）」。
- 边界：不为省内存牺牲速度。
- 依赖：R-GRID-02、R-IMP-05

## R-PERF-07 基准记录

- 优先级：P1
- 状态：已完成
- 行为：每次提交前跑 scripts/bench-record.py，结果追加到 docs/bench-history.md 一张表里，列包括日期、提交、机型、四个关键数字。
- 验收：
  - [x] 新增记录不改历史行
        2026-10-27 连跑两次，git diff 只有新增行，没有删除行；脚本写回后回读比对，除新增行外有任何差异就恢复原文件
  - [x] 数字退化超过 10% 时能在表里一眼看到
        退化项在单元格里标 ⚠️ +N%，终端另列一遍，退出码 1。2026-10-27 用一行人工构造的冷打开基线验证：500MB 打开 +22%、第 1 块 +12%、第 100 块 +25%，三项都标了出来
- 边界：不在 CI 里跑，手动执行。
- 依赖：R-PERF-05

实测（2026-10-27）：

| 项 | 结果 |
|---|---|
| 命令 | ./scripts/bench-record.py（构建 + 3 轮 + 追加），--from-logs 补录，--dry-run 预演 |
| 500MB 冷打开 | 3 轮中位 1.834 秒（1.872 / 1.834 / 1.536），峰值内存中位 1.26 GB |
| 第 1 块 / 第 100 块 | 0.123 / 0.125 秒 |
| 缓存隔离 | 每轮把 ParquetCache 指到空的临时目录，命中缓存时报错作废 |
| 历史行 | 10-23、10-24 两行逐字未变 |
| 噪声实例 | 负载 90 那次第 1 块 +13%、第 100 块 +24%；负载 33 复跑三项回落到 −15%/−1%/+4% |

为什么每轮要换缓存目录：500mb.csv 在这台机器上早有 Parquet 缓存，直接跑 bench.sh
量到的是 0.024 秒的缓存命中，写进表里就是假的冷打开。基准程序因此加了 --cache-dir
参数，只影响基准进程，应用本身仍用默认缓存目录。

为什么取 3 轮中位：同一提交同一台机器，500MB 冷打开量到过 1.872 和 1.536 秒，
差 18%。单次数字拿去比 10% 阈值，比的是一轮的运气。
