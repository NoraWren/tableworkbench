# 性能记录

每次提交前跑 `./scripts/bench-record.py`，它构建、跑基准、追加一行，并和同机型的上一行比。
只追加，不改历史行。

机器口径：M1 或更新、16 GB 内存以上、Apple 内建 SSD。换机器要另起一节。

## 怎么记

```
./scripts/bench-record.py              # 构建 + 跑 3 轮 + 追加一行
./scripts/bench-record.py --runs 5     # 跑 5 轮取中位
./scripts/bench-record.py --from-logs  # 不重跑，用 /tmp/tableworkbench-bench-measure.json 补录
./scripts/bench-record.py --dry-run    # 只打印要追加的行，不写文件
```

口径：

- 四项都取 3 轮中位。同一提交同一台机器，500MB 打开量到过 0.79 秒和 1.33 秒
  （见 10-24 那行的括号注），单次数字比 10% 比的是运气。
- 每一轮都把 Parquet 缓存指到一个空目录，量的必须是冷打开。500mb.csv 在这台机器上
  早有缓存，不换目录会量到 0.02 秒的缓存命中。
- 「500MB 打开」那一格带口径标记：「（冷打开）」或「（缓存）」。只和同口径的行比。
  10-23、10-24 两行没标过，脚本会把它们跳过并在终端说明，不拿它们当基线。
- 「提交」后面带 `+dirty` 表示记录时工作区有未提交改动，二进制不完全是这个提交的产物。
- 脚本跑之前记一行 1 分钟负载。这台机器 8 核，负载过 8 就是超载；退化项如果出现在
  这样的负载下，先复跑一次再说要不要查代码。

判定与退出码：

| 退出码 | 含义 |
|---|---|
| 0 | 追加成功，四项都在 10% 以内（或没有同口径基线） |
| 1 | 追加成功，但有项比基线慢（或高）超过 10% |
| 2 | 基准或日志缺失、JSON 不合法，表一个字节都没动 |
| 3 | 回读比对失败，文件已恢复原样 |

退化超过 10% 时，单元格里标 `⚠️ +N%`，终端再列一遍，按「说明」段的要求写进提交说明。

`--from-logs` 连跑两次会追加两行一模一样的数，那是同一份测量记了两遍，不是两次测量。
脚本发现四项和表尾完全相同就不写，返回 0；确实要再记一行时加 `--force`。

省下来的三块：

1. 文本列不再拼 `avg/median/stddev_pop(TRY_CAST(x AS DOUBLE))`。这三个指标在文本列上界面本来就不显示，却要把千万行转 DOUBLE 再排序求中位数。区域列因此从 0.34–0.55 秒降到 0.13 秒。
2. top-values 从 `GROUP BY CAST(x AS VARCHAR)` 改成 `GROUP BY x`、只在输出时转字符串。金额列从 0.41 秒降到 0.22–0.28 秒。
3. 文本列的类型冲突提示改成非空行超过 20 万时只扫前 20 万行，0.33–0.48 秒降到 0.03–0.04 秒。它是 P2 提示，界面上写明“只看了前 200000 行，行数按比例推算”。

顺带否掉近似去重。这个版本（DuckDB 1.1.3 + duckdb-swift 1.1.3）的 `approx_count_distinct` 误差不可用，而且比精确计数还慢：

| 数据 | 精确 | 近似 | 误差 | 精确耗时 | 近似耗时 |
|---|---|---|---|---|---|
| 区域（5 个值） | 5 | 4 | −20% | 0.12 s | — |
| 客户名称（977 个值） | 977 | 1032 | +5.6% | 0.08 s | 0.11 s |
| 金额（533 万） | 5,335,465 | 6,595,346 | +23.6% | 0.28 s | 0.04 s |
| 订单号（1017 万，全唯一） | 10,170,000 | 12,480,016 | +22.7%，比总行数还大 | 0.25 s | 0.07 s |
| 1000 万连续整数（无表） | 10,000,000 | 9,008,951 | −9.9% | — | 0.36 s |

`approx_count_distinct(hash(x))` 也不准：订单号报 8,265,904，误差 −18.7%。传第二个精度参数直接绑定报错，这个版本只接受单参数。结论是回到精确 `count(DISTINCT)`，`ColumnStats.distinctIsApproximate` 字段保留但当前恒为 false，规格里那条“允许近似但要标近似”保留，实现不使用。

分桶错位的根因与修法：`CAST(... AS INTEGER)` 返回 INTEGER，duckdb-swift 的 `cast(to: Int64.self)` 对 INTEGER 每行都返回 nil，`?? 0` 把千万行全算成第 0 桶。改成 SQL 里显式 `CAST(... AS BIGINT)`。修完之后 20 根柱子的行数之和等于非空行数，最大值落在最后一根柱子上，逐桶与手写区间 SQL 一致。时间列按天聚合的 `count` 是同一个坑（全部显示 0），一并改了。

## 滚动帧耗时（2026-10-24 19:05）

没有 Xcode，Instruments 的 Core Animation 用不了。改用仓库里的 TableWorkbenchScrollBench：离屏窗口托管真正的 DataGridView，按 60Hz 连续把滚动偏移下移 24 点，每次强制布局与绘制，记主线程这一段耗时。命令：./scripts/bench-scroll.sh。

口径要说清楚：这是应用自己每帧的布局 + 绘制时间，不含显卡合成与垂直同步，和 Instruments 的“掉帧率”不是同一个数，通常偏乐观。60fps 的预算是每帧 16.7 毫秒。

| 样本 | 滚动次数 | 中位 | p95 | 最大 | 超过 16.7 ms |
|---|---|---|---|---|---|
| wide-100k（10 万行 × 20 列） | 300 | 2.42 ms | 2.74 ms | 25.5 ms | 1 帧（0.3%） |
| 500mb（328 万行 × 20 列） | 300 | 2.67 ms | 2.99 ms | 26.1 ms | 1 帧（0.3%） |

## 内存（2026-10-27）

R-PERF-06 剩下两条验收此前没有测量手段，补了 `TableWorkbenchMemoryBench` 与 `scripts/bench-memory.sh`。
这一节先讲清口径，因为口径不钉死，后面的数都站不住。

| +1800 秒（末值） | 1 MB | 3 MB | 7 MB | −61 MB |

1800 秒共 30 个采样点，匿名页在 +180 秒就落到 6 MB，之后一直在 0–1 MB 之间平着，
末值 1 MB，相对起始 −61 MB，全程最大相对涨幅 +0 MB。判定通过。
RSS 从 494 MB 掉到 7 MB，再一次说明开头那个高值是文件页和还没回收的页，不是常驻占用。

定位过程中排除的四个猜想，记下来免得下轮再试：

| 变量 | 做法 | 结果 |
|---|---|---|
| 是不是开关本身漏 | 改成只开不查（临时改程序，跑完撤回） | 1 GB Parquet 20 轮稳定 9 MB；wide-3000 40 轮稳定 272 MB |
| 是不是取块漏 | 单会话连取 40 次块 | 377 → 211 MB，峰值 481 MB，无单调上涨 |
| 是不是 DuckDB 缓冲池 | `memory_limit` 降到 300MB | 60 轮仍爬到 965 MB 后回落，不跟着上限走 |
| 是不是线程工作内存 | `threads=2` | 曲线与默认一致，无可解释改善 |

跨会话连开 100 次 wide-3000.parquet 的曲线也说明它有顶：前 20 轮爬到约 1300 MB，
后 30 轮每轮 ±6 MB 基本持平，不是线性泄漏。

## CSV 冷打开（2026-10-27）

R-PERF-01 第一条在这里翻身。前面几轮一直以为瓶颈是 CSV 解析吞吐本身（R-DEC-16 就是这么写的），

被否掉的一条快路：preserve_insertion_order=false 全并行能把打开干到 0.80–0.81 秒，

### 0.52 秒花在哪

临时在 `exec`、`App.init`、`applicationWillFinishLaunching`、
`applicationDidFinishLaunching`、窗口出现各打一个点，记
`ProcessInfo.systemUptime`，与父进程的 mach 绝对时间对齐后相减。同时写了一个
70 KB 的最小 SwiftUI 空窗口 app 做对照，用来分清「我们的代码慢」和「AppKit 本来就这样」。

| 阶段 | 本项目 | 最小 SwiftUI 空窗口 | 差值 |
|---|---|---|---|
| exec → App.init | 0.013 | 0.007 | 0.006 |
| → willFinishLaunching | 0.105 | 0.099 | 0.006 |
| → didFinishLaunching | 0.245 | 0.102 | **0.143** |
| → 窗口出现 | 0.065 | 0.020 | 0.045 |
| 合计 | 约 0.43 | 约 0.23 | 约 0.20 |

这是直接 exec 的口径，比 `open -a` 少约 0.09 秒的 launchd 开销，所以 0.43 对得上
脚本量的 0.50 左右。

MenuBarClientCore 也在这期间做软链接加载。看得出来这是系统菜单构建的开销，
不是业务逻辑。能不能绕开**没验**——那要改菜单的构建方式，动的是产品要的菜单项与快捷键。

## 首屏取块改用 LIMIT/OFFSET，冷开降到 1.91 秒（2026-10-28）

下一节记的 2.8–2.9 秒作废，原因是口径错了：那次跑的构建产物是 debug（132 MB，和 scratch 里的 debug 二进制同尺寸；release 是 58 MB）。这一节全部是 release。

测量方法也换了。录屏逐帧算只能拿到粗粒度结果，还容易被自动拖拽的偶发失败带偏。现在在应用里打点：设 TW_OPEN_TIMING 后，OpenTiming 把「松手 / 物化 __base / DESCRIBE / count(*) / 会话就绪 / 首块 / 表格首帧」都按相对秒数写进标准错误，TW_OPEN_TIMING_FILE 设了就同时写文件。拖放松手那一刻起点归零，外部脚本不参与计时，只负责把文件拖进去，再用打点文件判断这一轮是否有效。

五次冷开（release，每次清空 Parquet 缓存、确认单实例、从访达拖入 500mb.csv，3,266,000 行）：

| 轮次 | 松手 → 表格首帧 | 其中物化 __base |
|---|---|---|
| 1 | 2.148 s | 1.824 s |
| 2 | 1.890 s | 1.582 s |
| 3 | 1.936 s | 1.643 s |
| 4 | 1.912 s | 1.602 s |
| 5 | 1.871 s | 1.571 s |
| 中位 | **1.912 s** | 1.602 s |

一次典型的分段：物化 1.57–1.82 秒 → 视图搭建 0.65 秒（改前）→ 首块 0.03 秒 → 首帧绘制 0.21 秒。

改了两处：

1. **取块 SQL**。原来对物化表用 `WHERE rowid >= a AND rowid < b ORDER BY rowid`。DuckDB 的 rowid 是虚拟列，过滤用不上统计信息，等于每取一块都把 326 万行扫一遍：实测 `WHERE rowid >= 0 AND rowid < 5000` 要 0.40 秒。改成 `LIMIT size OFFSET offset` 之后第 1 块 0.03 秒、第 100 块 0.09 秒、第 200 块 0.14 秒，每个位置都比 rowid 过滤快。物化表按插入序返回（DuckDB 默认 preserve_insertion_order），__result 的插入序就是排序后的顺序，行序不变。Parquet 视图那条路没动，仍按 __rid 过滤。
2. **NSTableView 接数据源**。`tableView.dataSource = ...` 这一行，AppKit 会按 numberOfRows 把 326 万行记进内部结构，实测 0.57 秒，占掉首屏四分之一的时间。改成先按 0 行接上、视图搭完再 reloadData 带真实行数，同样的 326 万行在 reloadData 里只要 2 毫秒。

试过但不成立的：给 __base 加一列 `row_number() OVER () AS __rid` 想靠 row group 裁剪，物化从 1.6 秒涨到 5.2 秒，取块没变快，撤回；把导入期内存上限留着不收回，取块时间不变；关掉后台转 Parquet 排除抢占，也没有变化。

回归检查：取块路径改动后跑滚动基准，300 帧均值 1.21 ms、p95 1.34 ms，超过 16.7 ms 的帧 0 个；TableWorkbenchTests 全绿，排在排序之后的取块与导出断言都覆盖到了。

没做到的：最慢那轮 2.148 秒，超预算超在物化那一段（1.82 秒），CSV 解析本身还没优化。缓存命中的 Parquet 视图首块仍是 0.7 秒，二次打开总耗时 0.73 秒，在 1 秒预算内但不快，留给下一轮。

## 拖入 500MB CSV 到出表（2026-10-28）

> 更正：这一轮跑的是 debug 产物，数字与结论作废，见上一节。

R-IMP-01 的验收项是"从松手到表格可滚动不超过 2 秒"。之前只验过拖拽通路能不能走通，秒数没量过。这次量了一次冷开（清空 Parquet 缓存、重启应用、从访达拖入 500mb.csv，3,266,000 行）。

方法：30 fps 全屏录制，按窗口坐标裁出网格区域，逐帧算平均绝对差，找出「正在打开…」出现与表格绘制这两个跳变点；两点的时间差就是松手到出表。

| 项 | 实测 |
|---|---|
| 拖入前（空状态）→ 出现「正在打开…」 | 视频 t≈3.47 秒 |
| 「正在打开…」→ 表格行出现 | 视频 t≈6.30–6.43 秒 |
| 松手到出表 | **约 2.8–2.9 秒** |
| 预算（R-PERF-01） | ≤ 2 秒 |

结论：这一版超出预算约 0.9 秒。注意它和 bench-history 里 1.546 秒的口径不一样——那个是 `scripts/bench.sh` 用 TableWorkbenchBench 跑的无界面路径（打开到取到第一块），这里是带界面的完整路径，两者差约 1.3 秒，说明从"取到第一块"到"表格画出来"之间还有一段可查的开销。

没做到的：只成功采到一次可用的冷开（第二次录制里文件没落到被录的实例上，帧里没有表格出现的跳变），样本量 1，不足以下结论，至少要 5 次取中位才算数。这套"录屏 + 帧差"的自动化也不够稳，取样前要先确认应用实例唯一且文件确实加载了。

## Instruments 可用性摸底（2026-10-28）

装好 Xcode 27.1 之后先摸清 xctrace 这台机器上能采什么，别等到要出数字时才发现采不到。结论按"能用/不能用"记。

能采：

| 模板 | 结果 | 备注 |
|---|---|---|
| Time Profiler | 11 MB trace，有 time-profile 表 | `--launch` 模式（把 .app 包交给 xctrace 启动）能采到 |
| Allocations | 9.2 MB trace，有 event_data | 同上 |
| System Trace（all-processes） | 37 MB trace，有数据 | `--all-processes` 模式 |

采不到：

- **Animation Hitches**：`--launch` 与 `--attach` 两种模式都只产出 40 KB 空壳（只有 RunIssues，没有 instrument_data），导出报 `Document Missing Template Error`。这个模板在 macOS 上对这类 AppKit 表格应用拿不到帧级数据，说明"滚动每帧耗时"这条还是只能靠自建的离屏基准加 ffmpeg 帧差，Instruments 补不上。
- **`--attach <pid>`**：同样是空壳。`DevToolsSecurity -status` 报 `Developer mode is currently disabled`（当前用户其实已在 `_developer` 组里），要 `sudo DevToolsSecurity -enable` 或到"系统设置 → 隐私与安全性 → 开发者模式"打开才行，这一步要管理员密码。

第一次跑 Time Profiler 只拿到启动阶段的 553 个主线程样本（状态全 Running），滚动那几秒没进来。原因是 xctrace 自己起了一个实例，而动作是发给 `open -a` 起的另一个实例（当时 `pgrep` 数到 3 个进程）。要采滚动就有两条路：开开发者模式后 attach 到已经打开文件的实例；或者保证单实例，改用应用内 Cmd+O 打开文件。
