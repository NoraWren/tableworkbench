# Design

## Context

见 proposal.md。`TextFileTranscoder.transcode(source:encoding:destination:)` 是导入链路的固定入口，`FileImporter` 只在编码需要转码时调用它。改动限制在这个函数内部。

## Goals / Non-Goals

**Goals:**

- 峰值内存与文件大小解耦。
- 分块边界不破坏多字节字符。
- 输出与整文件转码逐字节一致。

**Non-Goals:**

- 并行转码、断点续传、进度条。

## Decisions

### D1 固定 4 MB 块

一次读 4 MB。块太大省不了多少系统调用，块太小则切点计算变密。4 MB 在 155 MB 文件上是 38 块，边界开销可以忽略。

### D2 优先按换行切

0x0A 是 ASCII，不会出现在 GB18030 双字节或四字节字符的中间，也不会出现在 UTF-16 的任意半个码元里。切在换行之后一定是合法边界，而且让残留自然趋近于零。

### D3 没有换行时按规则扫描

用解码试探判断边界不可靠：系统解码器遇到半个字符会给出替换字符而不是返回 nil，测不出切偏。改成按字节规则扫描：GB18030 首字节 < 0x80 是单字节；次字节 0x30–0x39 说明是四字节；次字节 0x40–0xFE 且非 0x7F 是双字节。UTF-16 则取偶数长度，并把结尾的孤立高代理退回去。

### D4 残留跨块累积

每轮把上一轮的残留拼到新块前面再切。这样即使一块里一个换行都没有（例如超长单行），残留也不会无限增长——扫描一定会找到一个完整字符的结尾。

### D5 解码失败照旧报错

`String(data:encoding:)` 返回 nil 时仍然抛 `ImportError`，错误文案与原来一致，只是 technicalDetail 改成说明是分块解码失败。

## Risks / Trade-offs

- [残留导致的首块偏移] → 首块从文件开头读，不带残留，BOM 由独立路径处理。
- [切点扫描遇到非法字节] → 遇到非法次字节时按单字节前进，把错误留给解码器，不在转码层吞掉。
- [写出次数变多] → 每块一次 `write(contentsOf:)`，38 次写比一次写多几十微秒。

## Migration Plan

输出路径与文件内容语义不变，已生成的 Parquet 缓存无需重建。
