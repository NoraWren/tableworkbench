# Design

## 背景

R-PERF-01 第一条卡了很久，500 MB CSV 冷打开一直在 2.0–2.4 秒，预算 2 秒。
R-DEC-16 当时的归因是「耗时 99% 在 read_csv_auto 的全量解析，瓶颈是解析吞吐本身」，
依据是 usr 8.7 秒 / 墙钟 2.6 秒，看起来已经在并行。

这个归因错了一半。并行确实在跑，但被连接上的 memory_limit 压住了。

## 1. 怎么定位到内存上限

逐项排除进来的。先试的都是「让解析更快」的路子，全部无效：

| 方案 | 结果 |
|---|---|
| threads 1 / 2 / 4 / 8 | 4.33 / 3.08 / 约 2.0 / 约 2.0 秒 |
| force_compression='uncompressed' | 2.015 秒 |
| checkpoint_threshold='1GB' | 1.95 秒 |
| 先 COPY ... TO parquet 再读 | 3.56 秒，更慢 |
| sample_size / all_varchar / null_padding / buffer_size / store_rejects | 1.97–4.0 秒，或破坏行号定位 |

单线程 4.33 秒、双线程 3.08 秒说明解析本来就在并行，加线程没用；这些参数也都不动时间。
于是反过来做：把 memory_limit 当成自变量扫一遍。

## 2. 参数矩阵

500mb.csv 冷打开（每轮先清缓存），峰值 RSS 取整个打开过程：

| memory_limit | 打开秒 | 峰值 RSS |
|---|---|---|
| 1200MB | 1.96–2.08 | 1.18–1.30 GB |
| 1300MB | 1.96–2.08 | 1.18 GB |
| **1400MB** | **1.51–1.53** | **1.28–1.29 GB** |
| 1600MB | 1.52–1.62 | 1.29 GB |
| 2000MB | 1.47–1.66 | 1.34 GB |
| 3000MB | 1.59–1.84 | 1.40 GB |
| 4GB | 1.74–2.13 | 1.43 GB |

1400MB 是拐点：1300MB 还是旧的 2.0 秒，1400MB 直接掉到 1.5 秒；再往上时间不再变好，
峰值反而一路涨到 1.43 GB。所以取 1.4 GB，刚好够用。

其他数据集也跟着变好：

| 数据集 | 1200MB | 1400MB |
|---|---|---|
| 1gb.csv | 3.55–3.79 秒（峰值 1.55 GB） | 2.92–3.12 秒（峰值 1.73 GB） |
| 10m.csv | 5.27 秒（峰值 1.59 GB） | 4.80 秒（峰值 1.73 GB） |
| wide-3000.csv | 0.523 秒 | 0.431 秒 |
| 500mb.parquet / 1gb.parquet | 0.02 秒级 | 0.02 秒级，不受影响 |

## 3. 那 0.45 秒花在哪（未完全验清）

放开上限之后物化阶段快了一截。具体机制只能说个大概：

- `duckdb_temporary_files()` 全程 0 字节，所以不是肉眼可见的 spill 落盘。
- 单线程 4.33 秒、双线程 3.08 秒、默认 2.0 秒，说明线程数确实起作用，
  而 1200MB 恰好卡在「并行扫一遍 CSV 同时建表」这个工作集之下。
- 更像是被上限压住时并行度起不来，或者要反复回收缓冲区。这部分是推断，
  没有拿到 DuckDB 内部计数来证实。

写文档按这个分寸：时间是实测，机制是推断。不影响决策，因为拐点两侧都有重复测量。

## 4. 为什么做成两级上限

直接全局抬到 1.4 GB 也能达标，但常驻期也会多要 200 MB 的额度，而 R-PERF-06 关心的是
打开之后的静置占用和反复开关后的回落。导入是一次性的尖峰，常驻是长期的底噪，两者不该用同一个数。

所以导入期抬高、`CREATE TABLE "__base"` 一完成就 `SET memory_limit='1200MB'` 收回。
Parquet 走视图不物化（R-DEC-17），导入上限对它没意义；64 MB 以下的 CSV 也用不上，
不折腾。两个条件写在 `importMemoryLimit(for:)` 里。

## 5. 代价

1 GB CSV 的导入峰值从 1.55 GB 涨到 1.73 GB。R-PERF-06 量的是静置稳态匿名页，
不受影响（这一轮 bench-memory.sh 判定仍是通过：空载基线 662 MB，静置后 258 MB）。
将来如果有人要开 10 GB 级的 CSV，该给导入上限也加个天花板，而不是退回 1200MB。

## 6. 被否决的方案

- **preserve_insertion_order=false 全并行**：打开 0.80–0.81 秒，快一倍，但行序打乱
  （首行变成 A-000049815 / A-000199279）。网格第一屏、行号、复制粘贴全部失去意义。
- **物化后按 file_row_number 排回原位**：`read_csv_auto` 没有这个参数
  （Binder Error 列了全部候选），只有 Parquet 支持；要走这条路必须先转 Parquet，更慢。
- **全局抬到 4 GB**：打开反而慢（1.74–2.13 秒），峰值 1.43 GB。
- **按文件大小线性给额度**：实测拐点是台阶不是斜坡，1200→1300 都是 2.0 秒，
  1400 才掉下来，线性公式只会把简单事做复杂。
