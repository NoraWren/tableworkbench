# Design

## 背景

R-PERF-02 要求三件事：500 MB CSV 转 Parquet 不超过 20 秒、转换期间滚动和筛选可用、
转换中退出不损坏源文件。三条都没有测量手段，这次补上，并把测量过程中暴露的残留问题修掉。

## 1. 转换在哪跑

转换在 ParquetCache.scheduleConversion 里起一个 Task.detached(priority: .utility)，
里面新建独立的 in-memory DuckDB 连接，执行一条 COPY (SELECT * FROM read_csv_auto(...)) TO ... (FORMAT PARQUET)。

独立连接这点很关键：界面用的那个连接正在被网格读块，转换如果共用连接，滚动会和转换抢同一把锁。
现在两条连接互不相干，所以「转换期间滚动可用」几乎是结构上保证的，不是靠调优先级凑出来的。

## 2. 为什么量出来是 3.7 秒

实测三次 3.670 / 3.683 / 3.684 秒，方差极小。这个数字包含：

- 主进程已打开文件、建好会话之后，后台任务启动到产物改名完成；
- 内部连接 SET memory_limit='384MB'、SET threads=4；
- DuckDB 自己读 CSV、推断类型、写 SNAPPY 压缩的 Parquet。

不含进程启动和编码探测，那两项算在 R-PERF-01 的打开耗时里，不重复计。

bench-history 里 1.216 秒那个数字是导出通道，不设内存上限、不分块，不能和这里直接比，
所以这次没有拿它当结论。

## 3. 「转换期间可用」怎么证

两条独立证据，都不用眼睛看：

- 滚动：TableWorkbenchScrollBench 在缓存已就绪与缓存刚被删两种状态下各跑 5 秒 300 帧。
  有转换时 p95 1.13 毫秒，无转换 1.15 毫秒，超 16.7 毫秒的帧都是 0。
- 筛选：转换跑到 1.2 秒时另起一个进程做「区域=华东 + 按金额排序」，查询准备 0.928 秒，
  三个块各 0.06–0.07 秒，正常返回 652,606 行。

这是两个进程，不是同一个进程里并发。严格说它证明的是「转换不占用文件锁、不阻塞另一个读」。
第一条滚动证据补上了这个缺口：滚动基准是在同一进程里，一边转换一边滚。

## 4. 中断残留是真问题

kill -9 在 2.8 秒和 3.2 秒各杀一次，两种情况都留下 .parquet.tmp（20.8 MB、36.5 MB），
正式文件不存在，源文件 md5 前后一致。也就是说：数据是安全的，但磁盘会漏。

原有的清理逻辑只在下次转换开始时删自己那个 .tmp。可如果用户再也不打开同一个文件，
这个文件就永远躺在缓存目录里。而且 totalSizeBytes() 和 evictIfNeeded() 只认 .parquet 后缀，
这些残留既不计入 10 GB 上限，也不会被淘汰，等于绕过了容量约束。

修法三条，都很小：

1. 转换抛错时 defer 删掉临时文件，不等下一次。
2. 打开应用时清扫修改时间超过 1 小时的 .parquet.tmp。1 小时是为了不误伤正在写的——
   实测转换只要 3.7 秒，1 小时阈值留了三个数量级的余量。
3. totalSizeBytes() 和淘汰把 .tmp 计入，让 10 GB 是真实占用。

为什么不干脆把 .tmp 写进另一个目录：那样跨卷 rename 就不再是原子操作，
原子的 rename 会退化成复制，反而更容易出半截文件。同目录改名是这里唯一正确的做法。

## 5. 被否决的方案

- 用 duckdb 命令行量转换：量到的不是应用真实路径，而且拿不到同一批 SET 参数。
- 给转换加进度条：3.7 秒的活，进度条还没画完就结束了。
- 转换改成多线程分片：需求边界写明先单线程，且当前离预算有五倍余量。
- 把 .tmp 排除在容量之外「反正会被清」：实测证明它不会被清，这个假设本身就是这次的 bug。
