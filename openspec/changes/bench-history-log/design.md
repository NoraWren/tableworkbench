# Design

## 数据从哪来

三个来源，全在 `scripts/bench.sh` 一次运行的产物里：

| 数字 | 来源 |
|---|---|
| 500MB 打开 | `/tmp/tableworkbench-bench.log` 里 JSON 的 `openSeconds` |
| 峰值内存 | 同文件里 `/usr/bin/time -l` 的 `maximum resident set size` |
| 第 1 块 / 第 100 块 | JSON 的 `blocks` 里 `block == 1` 与 `block == 100` 的 `seconds` |

JSON 前后混着 `/usr/bin/time` 的统计行，所以先找第一个 `{` 再按花括号配平截一段。
不用正则去猜缩进。

`bench-record.py` 自己调 `bench.sh`，不重复实现构建和开跑的逻辑；这样两份数字
永远出自同一次运行，不会出现「打开时间是新构建、块耗时是旧构建」。

## 基线怎么取

基线 = 「记录」表里同一机型的最后一行，四个数字逐项比。

- 四项方向一致，都是越小越好，退化 = 新值 > 旧值 × 1.1。
- 严格大于才标；正好 10% 不标，留给噪声。
- 和基线相差 10% 以内也照实打印百分比，方便看趋势。
- 找不到同机型的行（第一次在这台机器上记），只追加，不比对，终端说明原因。
- 机型不同但表里有别的机型，同样不比对，并提示按 bench-history 的约定另起一节。

没有新建 `docs/bench-latest.json` 之类的状态文件。表本身就是状态，多一个文件就多
一处会和表不一致的地方。

## 只追加怎么保证

1. 用 `pathlib` 读全文，按行切。
2. 找到 `## 记录` 这一行，往下找到连续以 `|` 开头的一段，最后一行数据后面就是
   插入点。
3. 只做 `lines[:k] + [new_row] + lines[k:]` 的拼接，已有行原样保留（包括行尾空格和
   那两个括号注）。
4. 写完立刻回读，断言：新文件除多出一行外与旧文件逐行相同（`difflib` 比对，
   要求 diff 只有一条 `+`）。这条断言失败就不写。

## 退化怎么显示

标在单元格里，不新增列。新增列要改表头，改表头就是改历史行。

| 正常 | 退化 |
|---|---|
| `0.79 s` | `1.02 s ⚠️ +29%` |

终端另外打一份清单：

```
⚠️ 退化超过 10%：
  第 100 块   0.136 s → 0.192 s   +41%（基线 2026-10-24 / c5b2f72）
```

有退化时退出码 1，方便 `bench-record.py && git commit` 这种写法卡住。

## 退出码

| 码 | 含义 |
|---|---|
| 0 | 追加成功，四项都在 10% 以内（或没有可比基线） |
| 1 | 追加成功，但有项退化超过 10% |
| 2 | 基准或日志缺失，什么都没写 |
| 3 | 回读断言失败，文件保持原样 |

## 被否决的方案

- **直接改 `bench.sh` 让它自己写表。** bash 里解析 JSON 要么拉 jq 依赖，要么写一坨
  `grep`+`sed`，都不如 Python 清楚；而 `bench.sh` 还被 `bench-memory.sh` 之外的
  几个脚本单独调用，动它风险更大。
- **每次追加一节而不是一行。** 表已经是一行一次，改成小节会让「一眼看到退化」变成
  翻页找。
- **把基线存成 JSON 单独维护。** 两份状态必然分叉，表里明明已经有上次的数字。
- **用 git 提交号当基线键。** 同一个提交跑两次数字也不一样，提交号不解决可比性，
  机型才是。

## 验证步骤

1. `./scripts/bench-record.py --dry-run`：打印待追加行，`git diff` 必须为空。
2. `./scripts/bench-record.py`：追加一行，`git diff docs/bench-history.md` 只有一条 `+`。
3. 再跑一次：表里多一行，前三行逐字未变（`git diff` 仍是两条 `+`）。
4. 把基线那一行的第 100 块改成 `0.100 s`，`--dry-run` 必须报退化并返回 1；
   改回去，退出码回到 0。
