# Proposal

## Why

R-GRID-04 与 R-GRID-05 的两条秒数验收一直没达标：千万行排序 24.69 秒、等值筛选 1.51 秒。这轮打点拆开看，两条都卡在同一件事上——`CREATE TEMP TABLE __result AS SELECT ... ORDER BY` 这一句。把内存上限从常驻的 1200MB 抬到 4 GB 重跑，同样的数据 7 秒上下，说明大头是落盘，不是排序本身慢。

## What Changes

- 物化 `__result` 期间把 DuckDB 的 `memory_limit` 临时抬到 `min(物理内存的一半, 4 GB)`，建完用 `defer` 收回 1200MB。常驻占用不变，只有物化那一刻多占。
- 这样做的直接效果：千万行等值筛选 1.51 秒 → 0.86–0.89 秒，进了 1 秒预算；千万行排序 24.69 秒 → 5.15–7.82 秒，仍超 3 秒。
- `apply(view:)` 里补两个打点（物化开始 / 物化完成 / 计数完成），下次再查这一段不用重写计时。
- 不动「先物化再显示」这个模型。排序彻底进 3 秒要改成先按原表顺序出首屏、后台再物化，属于结构性改动，这轮不做。

## Capabilities

### Modified Capabilities

- `data-grid`：新增「大表筛选的等待上限」与「大表排序的顺序保证」两条契约。排序的秒数不写进契约，因为它现在还不达标，只写顺序与界面提示行为。

## Impact

- 代码：`DuckDBSession.apply(view:)` 加一次临时上限设置与一次 `defer` 还原，新增 `materializeMemoryLimit` 常量。
- 代价：物化那一刻峰值内存上升。10m.parquet 排序期间整进程 RSS 峰值 5.6 GB（16 GB 机器）；上限按物理内存的一半收窄，8 GB 机器上会自动降到 4 GB 以下。
- 验收：R-GRID-05 的 1 秒项可以勾了；R-GRID-04 的 3 秒项仍然不勾，数字改成 5.15–7.82 秒。
