# Proposal

## Why

千万行排序现在要 5–8 秒。R-DEC-23 把落盘的开销压下去之后，剩下的时间就是排序本身，靠调参数压不动了。但用户真正等的是「看见排好序的第一屏」：实测 `SELECT * FROM __base ORDER BY 金额 LIMIT 5000` 只要 0.61 秒，因为 DuckDB 对 ORDER BY + LIMIT 走的是堆式 top-N，不用把整表排完。整表物化只是为了后续滚动取块。

## What Changes

- 查询会话新增 `previewBlock(view:columns:limit:)`：只取排序/筛选后的前 5000 行，走 top-N 快路径。
- 网格模型在排序或筛选开始时，先把这个首屏取回来挂到条目上，界面立刻换成「已排序的前 5000 行」，同时显示「正在排序，先显示前 N 行」。后台照旧物化 `__result`，完成后再整体切换成完整结果并恢复真实行数。
- 只在表足够大（50 万行以上）且确实带排序或筛选时才做这一步，小表直接走原路径，避免闪一下。
- 首屏预览是临时态：切文件、换视图、物化失败都会清掉，不会留在界面上冒充最终结果。

## Capabilities

### Modified Capabilities

- `data-grid`：在「大表排序的顺序保证」里补一条——排序进行期间 SHALL 先给出已排序的首屏，并明确标识这是预览、总行数尚未确定。

## Impact

- 代码：`QuerySession` 协议加一个带默认实现的方法，`DuckDBSession` 实现它（复用取块的列投影逻辑），`WorkspaceModel` 加预览态与阈值，`ContentView` 在预览态下改用预览块并显示提示。
- 用户感知：千万行点列头，0.6 秒左右看到排好的第一屏，5–8 秒后总数与滚动范围补齐。
- 性能预算：排序的「点击到可滚动」从 5–8 秒降到 1 秒内（首屏），但总行数与完整结果仍要等物化完成，README 与验收口径要分开写。
