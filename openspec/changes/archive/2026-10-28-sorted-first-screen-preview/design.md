# Design

## 两次查询怎么分工

| 查询 | 用途 | 千万行实测 |
|---|---|---|
| `SELECT <显示列> FROM __base [WHERE] [ORDER BY] LIMIT 5000` | 首屏 | 0.61 s |
| `CREATE TEMP TABLE __result AS SELECT ... ORDER BY ...` | 滚动取块、计数、导出 | 5.15–7.82 s |

两条都在后台线程跑，但顺序执行：先预览、后物化。原因是 `DuckDBSession` 用一把锁串行化所有查询，并行反而会互相等待。

## 为什么预览要是独立状态

预览块只有 5000 行，`resultCount` 仍是旧的（或未知）。如果把预览块直接塞进正常路径、行数照抄旧值，滚动条长度和实际内容会对不上。所以条目上单开一个 `preview` 字段：有它的时候网格用预览块加预览行数，状态栏说明「总行数还在算」。物化完成后清掉该字段，网格按 `.id` 重建。

## 阈值

50 万行以下不走预览：小表物化本来就是几十毫秒，先出预览只会让界面闪一下。

## 没采用的

- 预览期间禁用滚动：预览本身就有 5000 行可滚，禁掉反而更怪。
- 预览块与物化结果做增量衔接（先显示预览、再补后面）：DuckDB 没有「从已排序结果继续」的接口，衔接要靠重复排序，不划算。
- 排序期间先显示未排序数据：用户点的是排序，给出未排序的行会误导。
