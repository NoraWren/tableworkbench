# Design

## 问题一：INTEGER 读成 nil

DuckDB 的 `CAST(x AS INTEGER)` 返回 INTEGER，而 `duckdb-swift` 1.1.3 的 `column.cast(to: Int64.self)` 只对 BIGINT 有效，对 INTEGER 每一行都返回 nil。Swift 侧原本写 `bucketColumn[i] ?? 0`，于是所有行都进了第 0 桶；时间列的 `count` 同理变成 0。

修法是把桶号和计数在 SQL 里显式 `CAST(... AS BIGINT)`。这不是分桶公式的错，公式本身没问题，测试里用 `floor((v - lower) / step)` 手算逐桶比对，确保修完之后落点与手算一致。最后一桶用 `<=`，因为区间右界就是列最大值。

同时把这条坑记进决策：`cast(to: Int64.self)` 只读 BIGINT。全仓库扫过一遍，其余 `cast(to: Int64.self)` 的调用点（`count(*)`、`rowid`、`length`）DuckDB 都返回 BIGINT，安全。

## 问题二：文本列白算数值聚合

原来的聚合 SQL 对任何列都拼 `avg/median/stddev_pop(TRY_CAST(x AS DOUBLE))`。文本列上这三个没有意义（界面也不显示），却要把千万行转 DOUBLE 再排序求中位数。1017 万行订单号列实测这一段占 0.36 秒。

改成按列类型拼 SQL：数值列拼三项数值聚合，文本列拼长度与空白统计，列读取用游标按顺序取，不再写死下标。

## 问题三：top-values 先把整列转字符串

`GROUP BY CAST(x AS VARCHAR)` 需要先物化千万行字符串再哈希。改成 `GROUP BY x`、只在 SELECT 里转字符串：金额列从 0.41 秒降到 0.22–0.28 秒。结果顺序用 `ORDER BY 2 DESC, 1 ASC` 保持稳定，值相同计数时按字符串升序。

## 问题四：类型冲突提示全表扫

类型冲突是 P2 提示，却要一次全表 `TRY_CAST` 扫描（0.33–0.48 秒）。改成非空行超过 20 万时只扫前 20 万行，命中数字与非数字就按比例推算总数。

选前 20 万行而不是随机抽样，是因为 `LIMIT` 在 CSV 和 Parquet 上都是顺序读，0.04 秒；`USING SAMPLE` 的 reservoir 要 0.31–0.37 秒，system 采样行数不稳定。代价是数据有排序时前段不代表整体，所以界面上写明“前 200000 行抽样，数字行数按比例推算”，不给精确数字的错觉。30 万行、一半数字一半文本的混合列实测：数字 15 万行、非数字 15 万行，与真实分布一致。

## 问题五：检查器面板太窄，几处文案被截断或重复

实机截图看出来三件事，都在界面层修：

- 时间列同时渲染了“按天分布”和高频值两组，日期整批重复一遍。数据侧两个数组都有值，界面上时间列只保留按天分布，高频值那组只在非时间列出现。
- 类型冲突那句话把三件事塞进一行，300 点宽下被截断成“整列按文…”。拆成“N 行不是数字”和“M 行看着像数字，整列按文本处理”两行，并允许纵向撑开。
- 文本列的极值按字典序算，30 与 400 之间夹着 abc 时标签写“范围”会被读成数值区间。文本列改叫“字典序首尾”。

顺带把反例查询加了 `DISTINCT`：同一列里几十万行都是同一个 `abc` 时，取两条反例只会得到两行 `abc`，去重后才有意义。

## 被否决的方案

- 用 `approx_count_distinct` 省时间：实测误差到 22.7%（1017 万报 1248 万），且比精确计数还慢，否决。
- 用 `hash(x)` 再做近似计数：1017 万唯一文本报 826 万，误差 18.7%，否决。
- 给 `approx_count_distinct` 传第二个精度参数：这个版本只接受单参数，直接绑定报错。
- 把四段查询合成一条：合并后仍然要把每段结果分开读，收益只有 0.1 秒左右，但 SQL 会变得极难读，否决。
- 用 `USING SAMPLE` 给类型冲突抽样：比 `LIMIT` 慢 8 倍，否决。
- 给 top-values 用 `approx_top_k`：只返回值的数组不带计数，界面要显示占比，否决。

## 分工

- DuckDB：全部聚合、分组、分桶都在 SQL 里做，Swift 侧不碰原始行。
- Swift 封装：`columnStats` 拼 SQL、按游标顺序读列、组装 `ColumnStats`；耗时分段计时走 `TW_STATS_TIMING`。
- UI 线程：统计仍在 `Task.detached` 里跑，主线程只接结果；切换列时旧结果先清空，回来时校验列名与选中项没有变。
